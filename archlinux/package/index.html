Archlinux Package System

发表于 2024-04-10 本文字数： 3.3k 阅读时长 ≈ 3 分钟

In some sense, Archlinux is just a minimal Debian with nice package managers. This post discusses about how the package creating, hosting and installing work.

Introduction

In the daily use of Archlinux, you will inevitably need to install packages. Package managers let you do that. Package manager is an important feature for any Linux system.

Pacman

Archlinux presents pacman. pacman lets you install the “official” packages from packages with just one command.

Cleaning pacman cache:

After a few pacman -Syus, you would have downloaded a ton of compressed package binaries. Cache is stored under /var/cache/pacman/pkg. You have to clean up the cache directory so it won’t grow infinitely in size.

paccache is a script included in the pacman-contrib package. It is not a dependency of pacman, you have to install manually. pacman has its built-in way to clean up cache as well, which is too aggressive and not as flexible as paccache.

By default, paccache removes all cached versions for all installed and uninstalled packages, except for the most recent three. (Command 1)

You can override the number of versions to keep by option -k. (Command 2)

You can limit the target packages to uninstalled. (Command 3)

Makepkg

makepkg is a central script to Archlinux packaging. The normal workflow is that you write a PKGBUILD file that keeps all the build commands and metadata for software. Execute makepkg on it, then it automatically pulls the source, runs build commands and bundles the output into a single compressed tarball (in .pkg.tar.zst extension). The tarball can be installed to the system by pacman -U.

Some packages include PGP signatures alongside their source file. In such case, makepkg will automatically verify its integrity. But if the needed public key is not found in user’s keyring (pacman’s keyring is not used), it tries to import the missing PGP key via gpg. gpg searches keyservers it knows for the provided fingerprint. However, it reads /etc/resolv.conf directly. If you happen to have an empty one, import will fail and so will build of the package.

According to wiki, the recommended way is to set /etc/resolv.conf as a soft link to /run/systemd/resolve/stub-resolv.conf. This propagates the systemd-resolved managed configuration to all clients. stub-resolv.conf contains the local stub 127.0.0.53 as the only DNS server.

AUR

Having pacman is good engough. Even better, there is AUR (Arch User Repository), a community repository that hosts a diverse range of packages upgrading at a much faster pace than the official repository. AUR packages are uploaded by users. Anyone can submit a package with just a few steps.

Pacman packages are precompiled binary tarballs. An AUR package contains only the build instructions (PKGBUILD). You will build and install the package on your own system. Thus, you should be careful about what you are installing, and audit the build script if needed. The AUR and the repos are not fundamentally different in the way how they were built. They all rely on makepkg and PKGBUILD files. It is just that the repos packages are somehow more standard packages. They are already examined by developers and compiled for users to download.

You are able to install any AUR package from scratch. makepkg, a script included in the standard Arch installation, is all you need. AUR helpers like yay (Yet Another Yogurt) will make your life easier. yay automates the process of searching, pulling, resolving dependencies and building.
